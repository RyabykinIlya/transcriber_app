# Audio to speech transcriber

HTTP-сервис поверх WhisperX для транскрибации аудио. Работает с файлами, лежащими в смонтированной `MEDIA_FOLDER` (см. `-v` при запуске контейнера).

Под капотом — whisperX: https://github.com/m-bain/whisperX. Скопируйте `.env_example` в `.env`, измените значения переменных.

Если вы в РФ, то `wget`, `apt install` и `pip install` с сайтов nvidia будут падать из-за недоступности, поэтому нужно использовать прокси — включаем или выключаем в `Dockerfile` (строки `COPY .wgetrc`, `apt.conf`, `pip.conf`):

```
.wgetrc
apt.conf
pip.conf
```

Работает на 3070 Ti для любого размера и длины аудио с текущими параметрами. Если падает с ошибкой «недостаточно памяти» — уменьшайте `CHUNK_TARGET_MS` / `CHUNK_MAX_MS` в `.env` (нарезка адаптивная, см. ниже).

## Build image
```
docker build -t audio-transcriber app -f Dockerfile
```

## Run container
```
docker run -d --name audio-transcriber \
  --env-file /home/user/transcriber_app/.env-docker \
  --gpus all \
  -p 8565:8565 \
  -v /mnt/meeting_records/audio:/records \
  -v transcriber-hf-cache:/root/.cache/huggingface \
  audio-transcriber
```
Том `transcriber-hf-cache` хранит модели HuggingFace — они не перекачиваются заново при пересоздании контейнера.

### Переменные окружения
| Имя | Назначение | Default |
|---|---|---|
| `APP_PORT` | Порт Flask | `3000` |
| `APP_DEBUG` | Flask debug (в docker лучше `False` — reloader форкает процесс с GPU-контекстом) | `False` |
| `MEDIA_FOLDER` | Папка с аудио и артефактами (`.lock`, `_transcription.txt`, `_error.log`) | — |
| `CHUNK_TARGET_MS` | Целевой размер чанка; реальный рез — по ближайшей тишине в окне `CHUNK_SILENCE_SEARCH_MS` | `900000` (~15 мин) |
| `CHUNK_MIN_MS` | Минимальный размер чанка (мельче резы не делаются) | `120000` |
| `CHUNK_MAX_MS` | Максимальный размер чанка; записи короче прогоняются одним куском | `1800000` (~30 мин) |
| `CHUNK_SILENCE_SEARCH_MS` | Окно поиска тишины вокруг целевой точки реза | `30000` |
| `CHUNK_OVERLAP_MS` | Запас по краям слайса (нужен только если рез попал в речь — тишина рядом не нашлась) | `3000` |
| `CHUNK_MIN_SILENCE_MS` | Какая пауза считается тишиной для реза | `500` |
| `CHUNK_BISECT_MIN_MS` | До какого размера дробится чанк при повторных сбоях | `30000` |
| `BATCH_SIZE` | Whisper batch size. **Внимание: на 8 ГБ GPU (RTX 3070 Ti) `8` в сочетании с длинными чанками даёт ~20-кратный провал скорости (замерено), оптимум — `4`** | `4` |
| `ASR_BEAM_SIZE` | Beam size декодера (замерено: 8 не лучше 5) | `5` |
| `WHISPER_INITIAL_PROMPT` | Словарь-подсказка для распознавания (по умолчанию встроенный корпоративный глоссарий; пустая строка = выключить) | — |
| `WHISPER_HOTWORDS` | Словарь вторым каналом (по умолчанию выкл) | — |
| `COMPUTE_TYPE` | Whisper compute type | `float16` |
| `DEVICE` | `cuda` / `cpu` | `cuda` |
| `HF_TOKEN` | Токен HuggingFace (нужен для диаризации) | — |
| `DIARIZE_MAX_SPEAKERS` | Сколько голосов максимум искать, когда диаризация запускается без явного `speakers_count` (раньше здесь жёстко стояло 3 — это резало любую встречу до трёх голосов) | `8` |
| `PRELOAD` | `1` — загрузить модели при старте контейнера (первый запрос не медленный) | — |
| `LOGGING_LEVEL` | Уровень логов | `INFO` |

> Не ставьте `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` — замерено: ломает pyannote-эмбеддинги (`CUDA driver error: device not ready`).

> ⚠️ **Диаризатор выгружается после каждого файла.** Pyannote держит резидентно ~2.4 ГБ (замерено: 5436 → 7853 MiB из 8192). Если его не освобождать, следующий файл в очереди транскрибируется при ~340 МБ запаса и проваливается в медленный режим: 100 % GPU util при ~105 Вт, один и тот же 24-минутный чанк идёт **4927 с вместо 142 с** (замерено на одном и том же файле до и после исправления). Поэтому `_release_diarizer()` вызывается в `finally` и после диаризации, и после `/enroll_voice`: перезагрузка пайплайна стоит ~70 с раз на файл со спикерами — несравнимо дешевле этого хвоста.


> Легаси-переменная `CHUNK_LENGTH_MS` продолжает работать и действует как `CHUNK_TARGET_MS`, если новая не задана.

## API

Все аудио-файлы хранятся в `MEDIA_FOLDER`. Ниже `{audio_name}` — имя файла внутри этой папки (например, `2025-01-19_22-54-48.mp3`).

Пайплайн один и тот же для всех способов запуска:
1. создаётся `.lock`-файл — признак «в работе»; в него же пишется JSON-прогресс (`chunk`, `total`, `percent`, `stage`);
2. исходник **один раз** декодируется ffmpeg'ом в память (16 кГц mono, ~230 МБ на час записи) — без pydub и без лимита 4 ГБ, из-за которого раньше валились многочасовые записи;
3. планировщик режет запись на **несколько больших чанков** (цель `CHUNK_TARGET_MS`, границы `CHUNK_MIN_MS`..`CHUNK_MAX_MS`), причём каждый рез ставится на ближайшую тишину в окне `CHUNK_SILENCE_SEARCH_MS` — слова на границах не режутся. 40-минутная встреча = 3 чанка вместо 20, многочасовая запись = ~15-минутные куски;
4. каждый чанк — это numpy-слайс из памяти (плюс небольшой запас `CHUNK_OVERLAP_MS` на случай реза в речи). Сегмент принадлежит ровно одному чанку — по времени своего начала: ни дублей, ни потерь на стыках;
5. чанк прогоняется через Whisper + align; **при сбое** (CUDA-глюк, OOM) он повторяется и рекурсивно делится пополам до `CHUNK_BISECT_MIN_MS` — один плохой кусок больше не убивает всю оставшуюся встречу (упавшие интервалы попадают в `_error.log`, остальной текст сохраняется);
6. диаризация (если запрошена) гоняется **один раз по всей записи** — спикеры получают стабильные метки `SPEAKER_XX` от начала до конца, а не перенумеровываются в каждом чанке;
7. результат пишется в `{stem}_transcription.txt`;
8. `.lock` снимается по завершении; при ошибке пишется `{stem}_error.log`.

Параллельные транскрибации сериализуются внутренним локом (GPU один, 8 ГБ).

### `GET /`
Health check. Возвращает `OK`.

### `GET /get_transcription`
Запускает транскрибацию файла, **который уже лежит** в `MEDIA_FOLDER`.

Параметры (query или form):
- `audio_name` — имя файла в `MEDIA_FOLDER`;
- `speakers_count` — включить диаризацию с `max_speakers=N` (опционально);
- `initial_prompt` / `hotwords` — свой словарь для этого запроса (опционально, см. «Качество» ниже).

Ответы:
```
200 {"status": "OK", "statusfile": "{audio_name}.lock"}
200 {"status": "IN_PROGRESS", "message": "..."}   // уже запущен
200 {"status": "ERROR", "message": "File ... not found on host"}
```

Пример:
```
curl "http://0.0.0.0:8565/get_transcription?audio_name=2025-01-19_22-54-48.mp3"
```

### `POST /upload_and_transcribe`
Синхронный эндпоинт для внешних сервисов: принимает файл multipart-ом, прогоняет его через тот же пайплайн (chunk → Whisper → align) и возвращает текст прямо в ответе. Никакие артефакты в `MEDIA_FOLDER` не остаются — файл и чанки живут во временной директории и удаляются по завершении запроса.

Поведение при занятости: если параллельно уже идёт другая транскрибация, запрос **не обрывается** — сервис ждёт освобождения внутреннего лока до 10 секунд. Если за это время очередь не освободилась, возвращается `503 BUSY` (безопасно повторить позже).

Запрос:
- `Content-Type: multipart/form-data`
- поле `file` — аудио-файл (обязательно)
- поле `speakers_count` — включает диаризацию с `max_speakers=N` (опционально)
- поля `initial_prompt` / `hotwords` — свой словарь для этого запроса (опционально, см. «Качество» ниже)

Ответы:
```
200 {"status": "OK", "transcription_text": "<текст>", "speakers": [...]}
400 {"status": "ERROR", "message": "No file provided ..."}
503 {"status": "BUSY", "message": "Another transcription is in progress, try again later"}
500 {"status": "ERROR", "message": "<exception>"}
```

Пример:
```
curl -X POST http://0.0.0.0:8565/upload_and_transcribe \
  -F "file=@./meeting.mp3"
```

Поле `speakers` в ответе — то же самое, что отдаёт `/get_status` (см. ниже).

Замечание: транскрибация выполняется в рамках HTTP-запроса целиком, поэтому на клиенте нужно выставить достаточный read timeout (обычно несколько минут на час записи).

### `GET /get_status`
Опрос статуса ранее запущенной транскрибации.

Параметры:
- `statusfile` — значение из ответа `/get_transcription` (`{audio_name}.lock`).

Ответы:
```
200 {"status": "IN PROGRESS", "chunk": 3, "total": 7, "percent": 43, "stage": "..."}   // + JSON-прогресс из .lock
200 {"status": "OK", "transcription_text": "<текст>", "speakers": [...]}
200 {"status": "ERROR", "message": "..."}
```

`speakers` — разметка по голосам (пустой список `[]`, если диаризации не было; поле присутствует всегда):

```json
"speakers": [
  {"label": "SPEAKER_00", "name": "Илья Рябыкин", "score": 0.71,
   "total_sec": 430.2, "segments": 61,
   "embedding": [0.01, "..."], "windows": [[271.4, 291.0], [601.2, 619.5]]},
  {"label": "SPEAKER_02", "name": null, "score": 0.41, "total_sec": 88.3}
]
```

- `label` — **исходная** метка `SPEAKER_XX` до переименования: по ней клиент находит реплики в тексте;
- `name` — имя из галереи или `null`, если голос ниже порога;
- `score` — лучший косинус по всей галерее (`null` без диаризации);
- `total_sec`, `segments` — сколько спикер говорил и из скольких сегментов;
- `embedding` — L2-нормализованный вектор спикера (или `null`) — нужен для ретро-разметки прошлых расшифровок;
- `windows` — до 8 самых длинных **непрерывных** окон речи (`[[start,end], ...]`, по возрастанию), каждое ≤ 30 с, каждое ≥ 6 с, суммарно ≤ 180 с; соседние сегменты с зазором < 1.0 с считаются одним окном. Ровно это клиент присылает в `/enroll_voice`.

Важно: при статусе `OK` сервис удаляет `_transcription.txt` (и легаси-папку `_chunks/`, если осталась от старых версий) — текст нужно сохранить у вызывающей стороны после первого успешного ответа. **`{stem}_speakers.json` при этом НЕ удаляется**: по нему можно разметить спикеров уже после того, как текст забрали (и после того, как в галерею зачислили нового коллегу).

Пример:
```
curl "http://0.0.0.0:8565/get_status?statusfile=2025-01-19_22-54-48.mp3.lock"
```

## Качество

Замерено A/B на реальных встречах (large-v3, RTX 3070 Ti 8 ГБ):

| Приём | Эффект |
|---|---|
| `WHISPER_INITIAL_PROMPT` (глоссарий терминов) | ~2× больше правильно написанных терминов (`Runway` вместо `runway`, `C-Sharp`, `DMZ`), цена — 0 |
| `WHISPER_HOTWORDS` | тот же эффект вторым каналом; вместе с промптом — чуть лучше по редким аббревиатурам, чуть медленнее |
| `ASR_BEAM_SIZE=8` вместо 5 | **не даёт выигрыша** в качестве на замерах |
| `hallucination_silence_threshold=2.0`, ослабленный VAD | **хуже**: больше галлюцинаций + в 3 раза медленнее — не использовать |

Поэтому: biasing включён по умолчанию (встроенный корпоративный глоссарий), beam остаётся 5. Свои термины можно передать под конкретную встречу параметрами обоих эндпоинтов — модель не перезагружается, подмена дешёвая.

> ⚠️ Словарь списком — только в `hotwords`. Голый список терминов в `initial_prompt` модель воспринимает как «уже распознанный текст» и **дословно эхом галлюцинирует его в расшифровку** (замерено: `ЗНИ ФТТ ЗНИ ФТТ...` вместо речи). `initial_prompt` — только связной фразой, и то с осторожностью: начало выдачи может её повторять. Сервис пишет warning в лог, если кастомный `initial_prompt` короче 120 символов.

Остаток «железа» качества — это диаризация: метки `SPEAKER_XX:` сильно улучшают читаемость протоколов. Включается параметром `speakers_count` **или** непустой галереей голосов (см. ниже), лимит голосов — `DIARIZE_MAX_SPEAKERS`.

> ⚠️ Диаризация требует разового ручного шага: HF-токен из `.env-docker` должен получить доступ к gated-модели — открыть https://hf.co/pyannote/speaker-diarization-community-1 и принять условия. До этого сервис честно пишет warning в лог и отдаёт текст без спикеров. Альтернативная модель задаётся через `DIARIZE_MODEL`. Замерено: диаризация быстрая (~50 с на 38-минутную встречу). Диаризация всегда выполняется **после** транскрипции, и после неё пайплайн pyannote сразу выгружается (`_release_diarizer`): резидентный диаризатор оставляет whisper'у ~340 МБ и тот проваливается в медленный режим на почти полном GPU (см. предупреждение про VRAM выше).

### Галерея голосов (voiceprints)

Сервис узнаёт голоса коллег и подписывает их реплики именами вместо `SPEAKER_XX`. Голоса лежат в галерее — файл `MEDIA_FOLDER/voiceprints.json`:

```json
{
  "version": 2,
  "speakers": [
    {"id": "spk_7f3c1a", "name": "Дмитрий Морякин", "embedding": ["..."],
     "samples": 3, "sample_seconds": 71.4,
     "created_at": "2026-11-02 23:10:00", "updated_at": "2026-11-02 23:10:00"}
  ]
}
```

- `id` — стабильный, `spk_` + 6 hex; по нему ссылается Telegram-бот.
- **Имя — ключ уникальности** (case-insensitive, `.strip()`): повторное зачисление того же имени обновляет запись, а не создаёт вторую. Два человека с одинаковым именем не поддерживаются — пишите `Иван Петров (Омни)`.
- `embedding` — L2-нормализованный вектор pyannote (256 float).
- `samples` / `sample_seconds` — сколько окон и секунд речи накоплено.
- Повторное зачисление усредняет вектор с весом по числу семплов: `(old*samples + new) / (samples+1)`, затем снова L2.

Легаси-файл `MEDIA_FOLDER/voiceprint.json` (один слепок, старый формат) продолжает работать: он читается как галерея из одной записи, имя берётся из `SPEAKER_NAME`. Как только появляется `voiceprints.json`, легаси-файл перестаёт использоваться — но **не удаляется** автоматически, это делает человек.

Хранение галереи непустой меняет поведение пайплайна: диаризация запускается сама на каждом файле (как раньше с одним слепком), с `min_speakers=1` и `max_speakers=DIARIZE_MAX_SPEAKERS` (по умолчанию **8**), иначе — `speakers_count` из запроса. Раньше здесь безусловно стояло `3`, и любая встреча резалась на три голоса.

#### `POST /enroll_voice`

`multipart/form-data`, поля:

- `name` — обязательное, имя человека как его писать в протоколе;
- источник эмбеддинга, одно из двух:
  - `audio_name` + `windows` — имя файла в `MEDIA_FOLDER` и JSON-массив `[[start_sec, end_sec], ...]` секунд (**основной путь**: 15–25 с чистой непрерывной речи у спикера часто нет, а суммарно 3–5 минут есть всегда);
  - `file` — загруженный файл (fallback, как раньше);
- `max_speakers` — только для файла, по умолчанию `2`. Для окон всегда `1`.

Окна нормализуются: `start < end`, внутри файла, наложения снимаются (перекрытие обрезается), окно длиннее 30 с обрезается до 30 с с начала, окно короче 0.4 с отбрасывается. Дальше окна склеиваются в один массив с 0.15 с тишины между ними, и по склейке считается эмбеддинг: `pipeline(склейка, min_speakers=1, max_speakers=1, return_embeddings=True)`; если кластеров всё же получилось несколько — берётся самый длинный по речи. Вектор нормализуется по L2 и попадает в галерею.

Ответы:
```
200 {"status": "OK", "id": "spk_7f3c1a", "name": "Дмитрий Морякин", "samples": 3, "sample_seconds": 71.4}
400 {"status": "ERROR", "message": "No name provided ..." | "No source provided ..." | "Too little speech: 2.1s" | "Bad 'windows' JSON: ..."}
404 {"status": "ERROR", "message": "File <audio_name> not found on host"}
500 {"status": "ERROR", "message": "Enrollment failed: ..."}
```

Пример:
```bash
curl -X POST http://localhost:8565/enroll_voice \
  -F "name=Илья Рябыкин" \
  -F "audio_name=2026-11-01_10-00-00.mp3" \
  -F 'windows=[[271.4,291.0],[601.2,619.5],[903.0,931.0]]'
```

Диаризатор освобождается в `finally` (`_release_diarizer`) — см. предупреждение про VRAM выше.

#### `GET /voiceprints`

Галерея без эмбеддингов, по имени:
```
200 {"status": "OK", "speakers": [{"id": "...", "name": "...", "samples": 3,
     "sample_seconds": 71.4, "created_at": "...", "updated_at": "..."}]}
```

#### `POST /voiceprints/delete`

Поля `id` **или** `name` (form или JSON):
```
200 {"status": "OK", "deleted": "spk_7f3c1a"}
400 {"status": "ERROR", "message": "No id or name provided"}
404 {"status": "ERROR", "message": "Not found"}
```

#### `GET /voiceprints/match?embedding=<json>`

Принимает эмбеддинг (JSON-массив), сравнивает со всей галереей — нужно, чтобы подписать старую расшифровку после зачисления нового коллеги:
```
200 {"status": "OK", "matches": [{"id": "spk_...", "name": "...", "score": 0.71}, ...]}
400 {"status": "ERROR", "message": "No embedding provided" | "Bad embedding: ..."}
```
Отсортировано по убыванию косинуса.

#### Порог и скоры

Порог — `VOICE_MATCH_THRESHOLD` (по умолчанию `0.60`). Калибровка на реальных данных: свой голос в студийной записи ~1.0, на встрече ~0.71, чужие люди 0.13–0.37. Сравнение идёт с **каждой** записью галереи, побеждает максимальный косинус; `score >= threshold` — метка заменяется на имя, иначе остаётся `SPEAKER_XX`. Каждый скор пишется в лог строкой `Voice match SPEAKER_XX vs '<имя>': cos=0.712 => matched`.

Удаление голоса из галереи не переписывает прошлые расшифровки — они уже сохранены у клиента.

## Типовой сценарий интеграции из внешнего сервиса

1. `POST /upload_and_transcribe` с файлом → получить `statusfile`.
2. Периодически `GET /get_status?statusfile=...` (например, раз в 10–30 с).
3. При `status=OK` — забрать `transcription_text` и сохранить у себя.
4. При `status=ERROR` — залогировать `message`.
